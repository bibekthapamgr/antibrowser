# Profile portability matrix (milestone 03, step 8; sealed snapshots since milestone 07; session carry since ADR-0028)

Question: when a closed workspace profile is sealed as an encrypted snapshot and restored into a **new** profile
folder, what still works — site data, and now the profile's own signed-in sessions? Decision for v1:
[ADR-0028](adr/0028-cross-device-session-carry.md) (supersedes the "sessions do not travel" line of
[ADR-0002](adr/0002-profile-portability.md)).

Method: `portability_spike` in `apps/desktop/src-tauri/tests/browser.rs`. A profile "signs in" to a test page (a
real cookie, encrypted at rest by Chromium with the OS key store; plus localStorage and IndexedDB), closes cleanly,
and is sealed — **carrying its own sessions inside the encrypted snapshot** (ADR-0028): the cookie values are
decrypted with the source computer's own browser cookie key and stored as the sealed `cookies.json` member. On
restore the member is re-encrypted under the destination computer's own browser cookie key and written back, so the
browser opens already signed in. Restores use the same origin (`http://127.0.0.1:47615`) because browser storage is
keyed by scheme, host **and** port. "Other machine" means a fresh CI runner.

"Label" is what the app shows after that restore (`pb_sync::portability`, ADR-0028); "Label honest" checks that a
label promising kept sign-ins (`supported`) was given only where the cookie really survived, and that
`sign_in_required` kept site data. The runtime pipeline's `report` job fails on any dishonest row.

## Measured matrix (Chrome for Testing, runtime pipeline)

The table below is regenerated by the pipeline (`scripts/runtime/portability-report.mjs`) from each runner's
measured result. The Windows and macOS cross-device rows are now `supported` because the sessions are carried and
re-keyed; Linux stays `sign_in_required` (development/CI only — its password store is not machine-bound, so it is
not representative and is never promised). macOS Intel (`macos-x64`) has no runner and so is not promised.

| Source | Target | Machine | Cookie (session) | localStorage | IndexedDB | Label | Label honest |
|---|---|---|---|---|---|---|---|
| windows-x64 | windows-x64 | same, new folder | kept | kept | kept | supported | yes |
| windows-x64 | windows-x64 | other machine | kept (carried) | kept | kept | supported | yes |
| windows-x64 | macos-arm64 | other machine | kept (carried) | kept | kept | supported | yes |
| windows-x64 | linux-x64 | other machine | **lost** | kept | kept | sign-in required | yes |
| macos-arm64 | macos-arm64 | same, new folder | kept | kept | kept | supported | yes |
| macos-arm64 | macos-arm64 | other machine | kept (carried) | kept | kept | supported | yes |
| macos-arm64 | windows-x64 | other machine | kept (carried) | kept | kept | supported | yes |
| macos-arm64 | linux-x64 | other machine | **lost** | kept | kept | sign-in required | yes |
| linux-x64 | linux-x64 | same, new folder | kept | kept | kept | supported | yes |
| linux-x64 | linux-x64 | other machine | kept | kept | kept | sign-in required | yes |
| linux-x64 | windows-x64 | other machine | **lost** | kept | kept | sign-in required | yes |
| linux-x64 | macos-arm64 | other machine | **lost** | kept | kept | sign-in required | yes |

Every restored profile opened. The Windows/macOS "other machine" `supported` rows are the ones the pipeline must
confirm on each run: a mislabelled pair (a `supported` label whose cookie did not survive) fails the `report` job
and the `portability_spike` honesty assertion, turning the run red.

Confirmed locally (Chrome for Testing 141.0.7390.37, Linux): a signed-in profile sealed with the carried
`cookies.json` member restored into a new folder and opened still signed in on the same machine (`supported`), and
the simulated other machine opened with site data back and re-keyed sessions (labelled `sign_in_required`, since
Linux is never promised across devices). The Linux → Linux "other machine" cookie is kept either way because the
development key store is not machine-bound, which is exactly why Linux is not representative.

The third label, `unsupported`, is given before anything is downloaded: a snapshot from a newer browser major than
the one installed, no runtime installed, an unknown platform, or a newer snapshot format. Those restores are refused
and change nothing (tests in `crates/sync`).

## What this means
| Pair | Sessions (cookies) | Site data (localStorage, IndexedDB) | Why |
|---|---|---|---|
| Same device, new folder | **Kept** on all three OSes | Kept | Same OS user, same key store |
| Windows → another Windows PC | **Kept** (carried, re-keyed) | Kept | Sessions carried inside the encrypted snapshot; a fresh DPAPI key is minted for the destination and the cookies re-encrypted under it (ADR-0028) |
| Mac → another Mac | **Kept** (carried, re-keyed) | Kept | Sessions carried inside the encrypted snapshot; re-encrypted under the destination Mac's deterministic mock-keychain key (`--use-mock-keychain`, ADR-0028) |
| Windows ↔ Mac | **Kept** (carried, re-keyed) | Kept | The carried plaintext is OS-independent, so it re-encrypts under either scheme |
| Any pair involving Linux | Lost across devices | Kept | Linux is development-only; its password store is not machine-bound, so it is not representative and never promised |
| Windows app-bound (`v20`) cookies | Not carried → sign in again | Kept | App-bound encryption binds the key to an elevation service the standalone runtime does not run; such values are skipped, never downgraded. Chrome for Testing uses the `v10` per-profile key, so this does not arise in practice |

## Supported in v1 (backup vs session transfer)
| Operation | v1 support |
|---|---|
| Local last-good copy and restore on the same device | **Supported** (milestone 03; sealed with this device's keychain key since milestone 07). Local-only backups never carry sessions across devices |
| Restore a workspace profile on a different device, measured OS pair | **Supported**: opens already signed in. Windows x64 and macOS arm64, both directions and self (ADR-0028) |
| Restore a workspace profile on a different device, any other pair | Site data best effort; **sign in to sites again**. The app says "websites may ask you to sign in again" only for these restores |
| Restore into an older browser major version | Refused (downgrade guard). Newer versions first take a copy made by the old version |
