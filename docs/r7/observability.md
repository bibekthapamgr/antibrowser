# R7 — Observability and scaling

## What is recorded
| Signal | Where | Notes |
|---|---|---|
| Request id | every API answer (`x-request-id`), error bodies, workspace audit, platform audit | generated by the server; a client's own id is ignored |
| Structured logs | API (pino, redacted: no tokens, cookies, credentials), worker (one JSON line per event) | journald on the server |
| App launch, store open, browser spawn/ready | desktop, local only (`timings` table, newest 200 per kind, p50/p95 in **Diagnostics**) | never sent; a person shares it when reporting a problem |
| Sign-ups finished (24 h / 7 d) | console → Operations → Health | counts only |
| Checkout pending age | Health: open checkouts and the oldest | a checkout waiting for payment; a payment that never activated is the `paid_not_active` alert |
| Webhook failures | Operations → Payment provider events; alerts `event_failed`, `webhook_backlog`, `signature_failures` | |
| Lease renewal | Health: open profiles; leases that ran out without renewal (24 h) | lost connections, sleeping laptops |
| Snapshot sync | Health: saved / failed backups (24 h); alert `sync_failures` (≥ 10 failed uploads in an hour) | |
| Backup recency | Operations: last profile backup, off-site archiving; alert `backup_failing`; preflight `backup_recency`; `pb-backup status` exit 3 | |
| Oldest queued work | Health: oldest automation job; Operations: outbox oldest; alert `queue_backlog` (outbox > 15 min or job > 30 min) | |
| Failed restore | alert `restore_failed`, raised by `restore-drill.sh` when a drill fails, cleared when one passes | |

Alerts are raised and cleared by the worker every minute (`app.ops_watch()`, migration 0018) and shown in the console
(Alerts, Operations). They are not pushed to a phone yet: the owner checks the console daily during the pilot, and the
status page is updated by hand.

## Privacy
Only counts, times and ids; no e-mail addresses, names, page content or browsing data in metrics. No third-party
analytics. Any future non-essential analytics (product usage) needs opt-in consent first; the website has none.

## Scaling order (decided)
1. Measure (performance report), then optimize queries, indexes, caching and worker concurrency.
2. Metadata, authorization and lease decisions stay on the authoritative database (no cache decides access).
3. When load or availability needs it: a second API/worker instance, then a managed or separate PostgreSQL, then
   object storage off the VPS.
4. Until then the **single VPS is the failure domain**: a host outage is downtime; recovery is the off-site restore
   (RPO 15 min / RTO 4 h targets).
