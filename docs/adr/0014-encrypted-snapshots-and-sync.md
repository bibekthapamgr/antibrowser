# 0014 — Encrypted snapshots, backups and synchronization
Status: **Accepted (beta track)**. Date: 2026-10-13. Owner: technical lead + security owner. Implements ADR-0003
(option A) and ADR-0002 for milestone 07.

## Context
Milestone 07 adds recoverable encrypted snapshots of organization profiles, local sealed backups, version history,
retention, recoverable deletion and key rotation, with deterministic conflict handling. ADR-0003 chose
service-managed envelope encryption (not end-to-end); ADR-0002 limits what a restore on another computer keeps
(website data yes, sign-ins no).

## Decision
### Keys (envelope encryption, three levels)
| Level | What | Where it lives | Rotation |
|---|---|---|---|
| Root key | 256-bit AES key per root id | The key provider. v1: `local` provider = a file readable by the API's OS user only (`KMS_LOCAL_KEY_FILE`, `{"active", "keys"}`); development/test may pass the same JSON in the environment. A cloud KMS or HSM provider implements the same `RootKeyProvider` interface before paid launch (gate below) | Add a new active root key; the worker re-wraps every organization key version; retire the old root key when nothing uses it (`scripts/deploy/root-key.sh`) |
| Organization key version | 256-bit AES key per version, one active per organization | PostgreSQL `organization_key_versions.wrapped_key`, wrapped by the root key (AES-256-GCM, AAD `pb-root-wrap-v1` + org id, key version id, version) | Owner only, after a recent sign-in: new active version; retired versions' data keys are re-wrapped by the worker in batches; a retired version is destroyed (wrapped key erased) 30 days after it wraps nothing |
| Data key | 256-bit AES key per snapshot, generated by the API at init | Wrapped by the organization key (AAD `pb-data-key-v1` + org, profile, snapshot, key version ids) in `snapshot_manifests.wrapped_dek`. Unwrapped only for the device that started the upload (init, idempotent replay) or an authorized restore plan; never stored or logged unwrapped | Never re-used for a second file |

The device never sees an organization or root key. The window (webview) never sees a data key, signed URL or token.

### Sealed file format (`pb-seal`, scheme `aes-256-gcm-chunked-v1`, schema 1)
`"PBSEAL\0\x01"` · u32 big-endian header length · header JSON (scheme, kind `org-snapshot` | `local-backup`, org id,
profile id, object id, schema version, key version, chunk size 1 MiB, 7-byte random nonce prefix) · STREAM
(big-endian 32-bit counter + last-chunk flag) AES-256-GCM chunks of the zstd (level 3) compressed GNU tar of
`meta/{snapshot.json, settings.json}` and `user-data/…`. The whole prefix is the AAD of every chunk, so a header
change, a reordered, truncated or appended chunk, or a file sealed for another organization, profile, snapshot or key
version fails authentication. Audited RustCrypto crates (`aes-gcm` 0.11.1, `aead-stream` 0.6.0); no custom
cryptography.

What goes in: the closed profile's `user-data` minus an explicit exclusion list (caches, GPU/shader caches, crash
dumps, metrics, model stores, Safe Browsing lists, singleton and lock files), no links or special files, and the
profile's settings exported from the app database (start pages, website permissions, privacy settings; never proxies
or their logins). Downloads are never inside the profile folder, so they are never in a snapshot; they stay ordinary
files in the folder the user chose.

### Upload (device → API → storage → worker)
`LOCAL_DIRTY → PREPARING → UPLOADING → VERIFYING → COMMITTED` (or `CONFLICT`, `FAILED`, `CANCELED`):
1. Only after a verified clean shutdown (profile `stopped`, no browser process using the folder); the profile is held
   (busy + OS lock) only while it is sealed, and opening it cancels that step.
2. The device takes the profile lease (fencing token), then `POST …/snapshots/init` with an Idempotency-Key: the API
   checks `snapshot.commit`, the live lease, `base_version == head` (else 409 `VERSION_CONFLICT`) and the quota, creates
   the manifest and a multipart upload, and returns the data key once (a replay of the same request returns the same
   upload, the key unwrapped again).
3. Parts (16 MiB) go to signed URLs valid 15 minutes for one part of this device's upload; storage credentials never
   leave the server.
4. `POST …/commit` declares SHA-256, sizes and parts; the API checks the fencing token, the head version, the declared
   parts against storage and completes the upload. The worker then checks the stored object's size, sealed header
   binding and SHA-256, and in one transaction the fencing token, quota and a compare-and-set of the profile's head:
   one winner, never last-write-wins.
5. Every step is saved on the device (no secret in it), so a lost network or a killed app resumes; a resumed upload
   asks the server for the operation's state first and never commits twice. Losing the lease, an expired upload or a
   failed verification restarts under a new snapshot id (bounded). Uncommitted uploads expire after 24 hours; objects
   nothing refers to are erased after a 24-hour grace period.

### Restore
A restore plan (`snapshot.restore`, audited, rate limited) gives a signed download URL and the data key. The device
downloads (resumable with Range), checks size and SHA-256 against the manifest before decrypting, checks compatibility
(browser major not newer than installed, known platform and schema), authenticates, decrypts and unpacks into a fresh
`user-data.incoming` with archive safety checks, then switches folders while the profile is closed: the previous data
is moved to evidence (kept, never deleted), a failed switch moves it back, and a crash mid-switch is finished at the
next start. Opening the profile is refused until the restore is done. The result is labelled per ADR-0002:
`supported` (same enrolled device), `sign_in_required` (any other device), `unsupported` (older browser, unknown
platform or format).

### Conflicts
A conflict changes nothing: the newer snapshot stays the head, this computer keeps its data. The user chooses: upload
theirs as the newest (the other version stays in history), replace theirs with the newer one (current data kept as
evidence), or open the newer one as a separate local copy first.

### Local backups
The last-good copy (milestone 03) is sealed (`kind local-backup`) with a device key: 32 random bytes in the OS
keychain, created on first use, identified by a fingerprint bound into the header (a reset keychain is reported as
"key not available", never as damage). Without a usable keychain the copy stays plain, as before; the key is never
written to a file.

### Retention, quotas, deletion
Per organization: keep the head, everything from the last 24 hours and the newest snapshot of each of the last
`retention_days` UTC days (default 7); deleted profiles stay restorable for `trash_days` (default 30), then their
objects are erased and manifests kept as tombstones. The service operator sets `backup_quota_bytes` (default 20 GiB)
and `max_snapshot_bytes` (4 GiB). Policy changes need `backups.manage` and are audited.

### Interpretations of ADR-0003
- A restore plan needs `snapshot.restore`, not the lease: reading a snapshot does not race an upload (uploads are
  fenced). Lease-controlled opening and handoff are milestone 08.
- Devices do not cache wrapped keys: each restore asks for a fresh plan; the device keychain holds only the
  local-backup key and the session's refresh token.
- The first key provider is a protected local file on the customer's (self-hosted) server; a managed KMS/HSM provider
  is a gate for paid launch (milestone 12/14).

## Consequences
- Not end-to-end: the operator of the server (holder of the root key) can decrypt snapshots; every unwrap for a
  restore is audited. This is stated in the UI, the security model and the runbook.
- Losing the root key loses every organization backup on that server; the runbook makes an offline copy mandatory.
- Cross-device restores bring back website data but not sign-ins (ADR-0002); the UI says so after every restore.
