# Crypto design review — encrypted snapshots (milestone 07)

Scope: the sealed file format (`crates/seal`), key hierarchy and wrapping (`services/api/src/backup/keys.ts`), the
upload/verify/restore protocol (`services/api/src/routes/snapshots.ts`, `services/api/src/backup/jobs.ts`,
`crates/sync`) and local sealed backups (`crates/runtime/src/backup.rs`). Decision record: [ADR-0014](../adr/0014-encrypted-snapshots-and-sync.md).
Reviewer: implementation self-review against the milestone's rules; an independent review is a milestone 12 gate.
Date: 2026-10-13.

## Primitives
| Use | Primitive | Library | Notes |
|---|---|---|---|
| Snapshot and local backup content | AES-256-GCM in the STREAM construction (big-endian 32-bit chunk counter, last-chunk flag), 1 MiB plaintext chunks | `aes-gcm` 0.11.1, `aead-stream` 0.6.0 (RustCrypto) | Online authenticated encryption for multi-GB profiles; truncation, reordering and appending fail (last-chunk flag) |
| Key wrapping (root → organization key, organization key → data key) | AES-256-GCM, 96-bit random IV per wrap, versioned blob `v1 \| IV \| ciphertext \| tag` | Node.js `crypto` (OpenSSL) | AAD binds every wrap to its context (below) |
| Transport integrity | SHA-256 of the whole sealed file | `sha2` / Node `crypto` | Checked by the server before commit and by the device before decrypting |
| Compression | zstd level 3 (before encryption) | `zstd` 0.13 | See "compression" below |
| Randomness | OS CSPRNG | `getrandom` / Node `crypto.randomBytes` | Keys, nonce prefixes, IVs, ids |

No custom cryptography: only standard constructions from maintained libraries.

## Nonce uniqueness
- Data keys are generated per snapshot (server) or per device (local backups) and seal exactly one file at a time:
  a snapshot's data key is never used for a second file (a restarted upload gets a new snapshot id and a new key).
- Within a file, the nonce is `7-byte random prefix ‖ 32-bit counter ‖ last flag`; the counter is unique per chunk,
  so (key, nonce) never repeats within the file. The 2³² chunk limit (4 PiB at 1 MiB) is far above the 4 GiB
  snapshot limit.
- Local backups reuse the device key across backups; each file has a fresh random 56-bit prefix. The birthday bound
  for a prefix collision needs about 2²⁸ backups of one device, far beyond its lifetime (backups are at most daily per
  profile plus manual ones). Recorded as a known margin; schema 2 could derive a per-file key with HKDF.
- Key wraps use a fresh random 96-bit IV each time; each organization key wraps at most the snapshots of one
  organization (well below 2³² wraps per key).

## Binding (associated data)
| What | AAD | Attack it stops |
|---|---|---|
| Sealed file chunks | The full prefix: magic, header length, header JSON (scheme, kind, org id, profile id, object id, schema version, key version, chunk size, nonce prefix) | Moving a file to another organization/profile/snapshot, swapping in an older snapshot's object under a new manifest, editing the header, downgrading the scheme |
| Data key wrap | `pb-data-key-v1` + org id + profile id + snapshot id + key version id | Using a data key wrapped for one snapshot to open another; cross-tenant key substitution in the database |
| Organization key wrap | `pb-root-wrap-v1` + org id + key version id + version | Moving an organization key version to another organization |

The device opens a file only with the binding it expects (from the restore plan or its own local record), and the
header must match before any chunk is decrypted. A wrong key, a changed byte anywhere, or a wrong binding fails
closed: the destination folder is removed and the current profile is untouched (tests below).

## Compression before encryption
Compression can leak information through ciphertext length when an attacker can inject chosen data next to secrets
and observe sizes repeatedly (CRIME/BREACH). Here the plaintext is a closed browser profile sealed once per backup;
an attacker who controls web content could influence some stored data, but observes only the total size of an entire
profile snapshot, at most a few times a day, with no interactive oracle. The milestone requires compression before
encryption; the residual risk (coarse profile size changes) is accepted and listed below.

## Key custody and lifetime
- Root key: the `local` provider reads a file that must be owner-only (`chmod 600`, checked at start-up); fixture keys
  from this repository are refused outside development/test. A managed KMS/HSM provider is required before paid
  launch.
- Organization key versions: unwrapped only inside a request or a worker transaction, wiped (`Buffer.fill(0)`) after
  use. Rotation (owner, recent sign-in) re-wraps data keys in batches; destruction erases the wrapped key 30 days after
  a retired version wraps nothing.
- Data keys: generated by the API, returned only to the device that started the upload (init and its idempotent
  replay) or to an authorized restore plan; never stored unwrapped, never logged (`data_key`, `wrapped_key`,
  `wrapped_dek` are forbidden payload keys in logs, events and audit). On the device they live in memory as
  `SealKey` (zeroized on drop, redacted `Debug`) and are dropped as soon as the file is sealed or opened.
- Device key (local backups): 32 random bytes in the OS keychain; never written to a file; a fingerprint (16 hex of a
  domain-separated SHA-256) identifies it without revealing it.

## Protocol review
| Threat | Mitigation | Evidence |
|---|---|---|
| Another tenant downloads or restores a snapshot | Tenant resolution + `snapshot.restore` on every plan; out-of-reach ids get the same 404; signed URLs name one object and expire in 15 minutes | `cross-tenant.test.ts` (all snapshot routes), `real_api.rs` (another organization: NOT_FOUND) |
| Object substitution in storage | SHA-256 checked by the worker before commit and by the device before decrypting; header binding of the snapshot id | `sync-s3.test.ts` (replaced object fails verification), `crates/sync` tests (substitution → `DIGEST_MISMATCH`; with a forged manifest → `SEAL_WRONG_BINDING`) |
| Manifest tampering (digest/size changed in the database) | The header binding and GCM tags still fail | `crates/sync` tests (`SEAL_AUTHENTICATION_FAILED`, `SEAL_WRONG_BINDING`) |
| Lost update between two computers | Lease + fencing token for every upload; compare-and-set of the head version in the verifying transaction; 409 otherwise | `sync.test.ts` (concurrent commits: one winner, one conflict), `crates/sync` and desktop tests, `real_api.rs` |
| Replay of an upload | Idempotency-Key bound to a digest of the request; a replay returns the same upload; a different request with the same key is refused | `sync.test.ts` |
| Unsafe archive (traversal, links, device names, huge expansion) | Only `meta/` and `user-data/` members; relative paths without `..`, links, special files, `:`/`\`/NUL, Windows device names, trailing dots/spaces or duplicates; byte and file limits; unpack only into a fresh empty folder | `crates/seal/src/tests.rs` |
| Data key, signed URL or token in logs/UI | Shell-only endpoints (not allow-listed for the window); redacted types; forbidden payload keys | `crates/cloud` allow-list tests; `sync.test.ts` "secrets stay out of logs, audit and events" (request logs, audit details and outbox payloads searched for the data keys and the download URL) |
| Truncated/partial download used | Size and SHA-256 checked first; resumable download into a separate file; GCM last-chunk flag | `crates/sync` (download cut off → resumes; never unpacks a partial file) |

## Residual risks and open items
1. **Not end-to-end.** The holder of the root key (the server operator) can decrypt every snapshot; unwraps for
   restores are audited, but a malicious operator with database and key file access is out of scope. (ADR-0003.)
2. **Root key file on the server.** Protected by OS permissions only; a server compromise with root access exposes it.
   Managed KMS/HSM before paid launch; offline backup of the file is mandatory ([runbook](key-recovery-runbook.md)).
3. **Profiles in use are plaintext** to Chromium on the device (disk encryption recommended), and so is the restored
   `user-data` folder.
4. **Metadata**: storage sees object sizes, timing, organization and snapshot ids (in object keys and headers);
   compression makes the size track profile content coarsely.
5. **Memory hygiene in JavaScript**: Node buffers are zeroed after use, but strings derived from keys (base64 in JSON
   responses) are not; the desktop's JSON value holding a data key is dropped right after parsing but not zeroized.
6. **Local backup nonce margin** (above): acceptable for v1; schema 2 should derive per-file keys.
7. **Independent review**: required before paid launch (milestone 12), including the KMS provider and key destruction.
